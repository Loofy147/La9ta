واجهت النسخة الأولى مشكلة: كانت بعض نتائج البحث بلا رابط إعلان إنساني، وأمكن أن يظهر رابط API الخام لو استُخدم حقل `viewUrl` كاحتياط. عولج هذا في المصدر:

- أظهر فحص حي لاحق لبحث HOCO H29 رابط Ouedkniss حقيقيًا مطابقًا للمعرف `d56373493`.

لا يزال المصدر الخارجي قادرًا على التغير أو الانقطاع. السعر والتوفر ليسا مضمونين، ويجب إعادة التحقق منهما قبل التواصل النهائي.

## 5. الأثر الرجعي والحدود

- تغير كتالوج المنتجات لا ينبغي أن يعيد تسعير الطلبات التاريخية؛ كل طلب جديد يحفظ لقطة بيانات العرض وقت الإرسال.
- عروض البحث تحفظ بوصفها عروضًا خارجية، وسعرها لا يُضاف إلى المجموع المرجعي للكتالوج الثابت.
- أضيفت هوية موحدة لإعلان Ouedkniss لمنع ظهور الإعلان نفسه كسطرين إذا جاء من الكتالوج والبحث. اختبارات الوحدة لهذه الهوية نجحت، لكن اختبار واجهة تفاعلي بعد الإصلاح لا يزال مطلوبًا.
- واجهة الإدارة محمية على مستوى API، وقد ثبت الرفض بلا رمز فقط. نجاح الرمز الصحيح وتحديث حالة طلب محفوظ لم يُثبت بعد.
- ملفات PWA موجودة واستثناء مسارات الإدارة وAPI من التخزين المؤقت مضبوط في المصدر؛ التثبيت الفعلي وسلوك تحديث cache على هاتف لم يُختبرا بعد.
- لا يوجد دمج دفع إلكتروني أو شحن مثبت.
- لم يُجر أي تغيير alias على النطاق القديم، ولم يحدث نقل أو حذف للطلبات القديمة.

## 6. بوابات الإغلاق التالية

1. تنفيذ طلب اصطناعي في المعاينة ببيانات غير شخصية/اختبارية، ثم إثبات حفظه واسترجاعه وتحديث حالته، مع تنظيف السجل التجريبي دون المساس ببيانات إنتاج قديمة.
2. اختبار مصادقة الإدارة باستخدام رمز صحيح في بيئة المعاينة، وإثبات 401 للرمز المفقود والخاطئ.
3. إعادة اختبار السلة بعد إصلاح هوية الإعلان المكرر.
4. فحص Service Worker على متصفح هاتف، بما يشمل إصدار cache جديدًا وإبطال القديم.
5. مراجعة مصادر البحث الإضافية وشروط الاستخدام والحصص قبل إضافة مصدر ثانٍ.
6. كتابة قرار مستقل بشأن نقل النطاق أو بيانات الطلبات؛ لا يتم الانتقال الإنتاجي بشكل ضمني ضمن دمج التوثيق.
